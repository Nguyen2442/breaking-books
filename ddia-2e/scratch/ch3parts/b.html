3.9 · When to Use Which Model · Schema flexibility

Khi nào dùng mô hình nào, và schema nằm ở đâu When to Use Which Model

Tóm tắt

  • Document thắng ở schema linh hoạt, locality và gần với object trong code. Quan hệ thắng ở join, nhiều-một và nhiều-nhiều.
  • Dữ liệu dạng cây, thường tải cả cây, thì dùng document. Cắt cây ra nhiều bảng (shredding) làm schema và code rối.
  • “Schemaless” là cách gọi sai. Chính xác hơn là schema-on-read (schema ngầm, diễn giải lúc đọc), so với schema-on-write (schema tường minh, database kiểm tra lúc ghi).

Nếu dữ liệu có cấu trúc giống document (cây quan hệ một-nhiều, thường tải cả cây một lúc), mô hình document có lẽ hợp. Kỹ thuật quan hệ shredding, tức chia cấu trúc kiểu document thành nhiều bảng như positions, education, contact_info, dẫn tới schema cồng kềnh và code phức tạp không cần thiết.

Document cũng có giới hạn. Bạn không tham chiếu thẳng được tới một phần tử lồng bên trong, mà phải nói kiểu “phần tử thứ hai trong danh sách vị trí của user 251”. Nếu cần tham chiếu phần tử lồng, cách quan hệ tốt hơn vì mọi thứ đều có ID riêng. Ngược lại, với danh sách người dùng tự kéo thả sắp xếp (to-do list, issue tracker), document chỉ cần lưu mảng ID theo thứ tự. Database quan hệ không có cách chuẩn và phải dùng mẹo: cột số nguyên (phải đánh số lại khi chèn giữa), danh sách liên kết, hoặc fractional indexing.

Schema-on-read và schema-on-write

Hầu hết database document không ép schema lên document. Nhưng code đọc dữ liệu luôn giả định một cấu trúc nào đó, nên schema vẫn tồn tại, chỉ là ngầm định. Đó là schema-on-read, đối lập với schema-on-write của database quan hệ truyền thống. Hai cách này giống kiểm tra kiểu động (lúc chạy) và kiểm tra kiểu tĩnh (lúc biên dịch) trong ngôn ngữ lập trình, và cũng gây tranh cãi y như vậy. Không có đáp án đúng tuyệt đối.

Khác biệt lộ rõ khi đổi định dạng dữ liệu. Giả sử bạn đang lưu họ tên trong một trường name và muốn tách first_name riêng. Với document, bạn bắt đầu ghi document mới có trường mới, và code đọc xử lý document cũ:

if (user && user.name && !user.first_name) {
  // Documents written before Dec 8, 2023 don't have first_name
  user.first_name = user.name.split(" ")[0];
}

Nhược điểm: mọi phần code đọc database giờ phải xử lý document định dạng cũ, có thể được ghi từ rất lâu. Với schema-on-write, bạn chạy migration:

ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL;
UPDATE users SET first_name = split_part(name, ' ', 1);      -- PostgreSQL
UPDATE users SET first_name = substring_index(name, ' ', 1); -- MySQL

Thêm cột có giá trị mặc định thường nhanh, kể cả trên bảng lớn. Nhưng UPDATE phải viết lại mọi hàng nên có thể rất chậm. Có công cụ migration chạy nền không downtime, nhưng migration trên database lớn vẫn khó vận hành. Mẹo né: chỉ thêm cột mặc định NULL (nhanh) rồi điền lúc đọc, giống cách làm với document.

Schema-on-read có lợi khi dữ liệu không đồng nhất: nhiều loại object khác nhau mà không thể cho mỗi loại một bảng, hoặc cấu trúc do hệ thống bên ngoài quyết định và có thể đổi bất cứ lúc nào. Khi mọi bản ghi đều có cùng cấu trúc, schema là công cụ hữu ích để ghi lại và ép buộc cấu trúc đó.

Cạm bẫy

“Schemaless” không có nghĩa là không có schema. Nó có nghĩa là schema nằm rải rác trong code đọc dữ liệu thay vì nằm ở database. Cái giá phải trả chỉ được dời sang nơi khác.

3.10 · Data locality · Query languages for documents · Convergence

Locality, aggregation pipeline và sự hội tụ Data locality and query languages for documents

Tóm tắt

  • Document lưu thành một chuỗi liên tục. Đọc cả document thì nhanh, nhưng sửa một phần nhỏ thường phải ghi lại cả document. Vì vậy nên giữ document nhỏ.
  • Locality không độc quyền của document: Spanner (bảng xen kẽ), Oracle (cluster table), Bigtable/Cassandra/HBase (column family) cũng làm được.
  • MongoDB aggregation pipeline có sức diễn đạt gần một tập con của SQL, chỉ khác là viết bằng cú pháp JSON.

Document thường được mã hoá thành một chuỗi liên tục: JSON, XML hoặc dạng nhị phân như BSON của MongoDB. Nếu ứng dụng hay cần cả document (để render một trang), locality mang lại lợi thế hiệu năng. Lợi thế này chỉ có khi bạn cần phần lớn document cùng lúc: database thường phải nạp cả document dù bạn chỉ cần một mẩu, và khi cập nhật thì thường ghi lại toàn bộ. Vì vậy sách khuyên giữ document nhỏ và tránh cập nhật nhỏ liên tục.

Về ngôn ngữ truy vấn: XML có XQuery và XPath; JSON có JSON Pointer và JSONPath; MongoDB có aggregation pipeline. Ví dụ của sách: một nhà sinh học biển ghi lại mỗi lần thấy động vật ngoài khơi, giờ muốn báo cáo số cá mập thấy được mỗi tháng.

-- PostgreSQL
SELECT date_trunc('month', observation_timestamp) AS observation_month,
       sum(num_animals) AS total_animals
FROM observations
WHERE family = 'Sharks'
GROUP BY observation_month;
// MongoDB
db.observations.aggregate([
  { $match: { family: "Sharks" } },
  { $group: {
      _id: {
        year:  { $year:  "$observationTimestamp" },
        month: { $month: "$observationTimestamp" }
      },
      totalAnimals: { $sum: "$numAnimals" }
  } }
]);

date_trunc('month', timestamp) làm tròn timestamp xuống đầu tháng. Truy vấn lọc họ Sharks, nhóm theo tháng, rồi cộng số con mỗi tháng. Pipeline của MongoDB làm đúng ba việc đó, chỉ khác cú pháp. Chọn cái nào có lẽ là chuyện khẩu vị.

Hai mô hình đang hội tụ

Database quan hệ đã thêm kiểu JSON, toán tử truy vấn JSON và index trên thuộc tính trong document. Một số database document (MongoDB, Couchbase, RethinkDB) đã thêm join, secondary index và ngôn ngữ truy vấn khai báo. Đây là tin tốt: nhiều database document cần tham chiếu kiểu quan hệ, và nhiều database quan hệ có những phần cần schema linh hoạt. Kết hợp cả hai trong cùng database là một tổ hợp mạnh.

Trong sách

Bản mô tả gốc của Codd năm 1970 đã cho phép thứ gần giống JSON trong schema quan hệ, gọi là nonsimple domains: giá trị trong một hàng có thể là cả một relation lồng nhau. Hơn 30 năm sau SQL mới thêm hỗ trợ JSON/XML để làm điều tương tự.

3.11 · Graph-Like Data Models · Property Graphs

Khi mọi thứ đều có thể liên quan tới mọi thứ Graph-Like Data Models

Tóm tắt

  • Graph gồm đỉnh (vertex, node, entity) và cạnh (edge, relationship, arc). Hợp với dữ liệu nhiều quan hệ nhiều-nhiều phức tạp.
  • Property graph: mỗi đỉnh/cạnh có ID, nhãn (label) và các thuộc tính key-value. Có thể lưu bằng hai bảng quan hệ vertices và edges.
  • Graph linh hoạt: không schema nào giới hạn cái gì nối với cái gì, đi được cả hai chiều, và dễ mở rộng khi ứng dụng có thêm loại dữ liệu mới.

Nếu dữ liệu chủ yếu là quan hệ một-nhiều, document là phù hợp. Nếu quan hệ nhiều-nhiều rất phổ biến và ngày càng phức tạp, mô hình hoá thành graph trở nên tự nhiên hơn. Ví dụ quen thuộc: graph xã hội (đỉnh là người, cạnh là quen biết), graph web (đỉnh là trang, cạnh là link), mạng đường bộ (đỉnh là giao lộ, cạnh là đường). Các thuật toán nổi tiếng chạy trên chúng: tìm đường ngắn nhất cho app bản đồ, PageRank để xếp hạng trang web.

Graph biểu diễn được theo hai cách chính. Danh sách kề: mỗi đỉnh lưu ID các đỉnh hàng xóm cách một cạnh, hợp để duyệt graph. Ma trận kề: mảng hai chiều, hàng và cột là các đỉnh, ô bằng 1 nếu có cạnh, hợp với machine learning.

Graph không nhất thiết đồng nhất. Facebook duy trì một graph duy nhất với nhiều loại đỉnh (người, địa điểm, sự kiện, check-in, bình luận) và nhiều loại cạnh. Các knowledge graph của search engine ghi lại sự thật về tổ chức, người, nơi chốn.

Property graph

Trong mô hình property graph (Neo4j, Memgraph, KùzuDB…), mỗi đỉnh có ID duy nhất, một nhãn cho biết loại object, tập cạnh đi ra, tập cạnh đi vào, và các thuộc tính key-value. Mỗi cạnh có ID, đỉnh đuôi (nơi cạnh bắt đầu), đỉnh đầu (nơi cạnh kết thúc), nhãn mô tả quan hệ, và thuộc tính. Có thể hình dung graph store là hai bảng:

CREATE TABLE vertices (
    vertex_id   integer PRIMARY KEY,
    label       text,
    properties  jsonb
);
CREATE TABLE edges (
    edge_id     integer PRIMARY KEY,
    tail_vertex integer REFERENCES vertices (vertex_id),
    head_vertex integer REFERENCES vertices (vertex_id),
    label       text,
    properties  jsonb
);
CREATE INDEX edges_tails ON edges (tail_vertex);
CREATE INDEX edges_heads ON edges (head_vertex);

Ba điểm quan trọng: (1) đỉnh nào cũng nối được với đỉnh nào, không có schema giới hạn; (2) từ một đỉnh tìm được cả cạnh vào lẫn cạnh ra, nên duyệt được cả xuôi lẫn ngược (vì thế có index trên cả hai cột); (3) dùng nhãn khác nhau cho các loại đỉnh/cạnh, bạn lưu nhiều loại thông tin trong một graph mà mô hình vẫn gọn. Bảng edges chính là bảng nối nhiều-nhiều, được tổng quát hoá cho nhiều loại quan hệ.

Graph ví dụ của sách (Hình 3-6): Lucy sinh ở Idaho, Alain sinh ở Saint-Lô (Pháp), hai người kết hôn và sống ở London. Graph thể hiện dễ dàng những thứ khó đưa vào schema quan hệ: cấu trúc vùng khác nhau giữa các nước (Pháp có département và région, Mỹ có county và state), một quốc gia nằm trong quốc gia khác (England trong United Kingdom), và độ chi tiết khác nhau (nơi ở của Lucy là thành phố, nơi sinh chỉ là bang).

Ghi nhớ

Graph rất hợp cho khả năng tiến hoá (evolvability). Muốn ghi dị ứng thực phẩm? Thêm đỉnh cho từng chất gây dị ứng, cạnh từ người tới chất đó, rồi cạnh từ chất tới món ăn chứa nó, và bạn truy vấn được món nào an toàn cho ai. Graph cũ không phải đổi gì.

Cạm bẫy

Một cạnh chỉ nối đúng hai đỉnh. Bảng nối quan hệ thì có thể biểu diễn quan hệ ba chiều trở lên bằng nhiều khoá ngoại trên một hàng. Trong graph, bạn phải tạo thêm một đỉnh đại diện cho “hàng” đó, hoặc dùng hypergraph.

3.12 · The Cypher Query Language · Graph Queries in SQL

Cypher: 4 dòng, SQL: 31 dòng The Cypher Query Language and Graph Queries in SQL

Tóm tắt

  • Cypher là ngôn ngữ truy vấn property graph (ra đời ở Neo4j, nay là openCypher). Nó dùng ký hiệu mũi tên: (idaho) -[:WITHIN]-> (usa).
  • -[:WITHIN*0..]-> nghĩa là “đi theo cạnh WITHIN không hoặc nhiều lần”, giống dấu * trong regex. Số bước join vì thế không biết trước.
  • SQL làm được bằng WITH RECURSIVE, nhưng cùng truy vấn tốn 31 dòng thay vì 4. Chọn đúng mô hình và ngôn ngữ tạo khác biệt lớn.

Cypher được Neo4j tạo ra, sau thành chuẩn mở openCypher, được Memgraph, KùzuDB, Amazon Neptune, Apache AGE hỗ trợ. Tên lấy từ một nhân vật trong phim The Matrix, không liên quan tới mật mã học. Chèn một phần graph:

CREATE
  (namerica :Location {name:'North America', type:'continent'}),
  (usa      :Location {name:'United States', type:'country'  }),
  (idaho    :Location {name:'Idaho',         type:'state'    }),
  (lucy     :Person   {name:'Lucy' }),
  (idaho) -[:WITHIN ]-> (usa)  -[:WITHIN]-> (namerica),
  (lucy)  -[:BORN_IN]-> (idaho)

Câu hỏi: tìm tên những người di cư từ Mỹ sang châu Âu, tức là có cạnh BORN_IN tới một nơi nằm trong Mỹ và cạnh LIVES_IN tới một nơi nằm trong châu Âu:

MATCH
  (person) -[:BORN_IN]->  () -[:WITHIN*0..]-> (:Location {name:'United States'}),
  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name

Có nhiều cách thực thi. Cách 1: quét mọi người, kiểm tra nơi sinh và nơi ở của từng người. Cách 2: đi ngược từ hai đỉnh Location. Nếu có index trên name, tìm nhanh đỉnh US và Europe, rồi đi theo mọi cạnh WITHIN đi vào để có mọi bang, vùng, thành phố bên trong, cuối cùng tìm người qua cạnh BORN_IN/LIVES_IN đi vào. Vì Cypher là khai báo, bộ tối ưu tự chọn cách.

Truy vấn graph bằng SQL

Mỗi cạnh duyệt qua tương đương một join với bảng edges. Trong SQL bạn thường biết trước cần join gì. Trong truy vấn graph, LIVES_IN có thể trỏ tới con phố, thành phố, vùng hay bang, nên số bước không cố định. Từ SQL:1999, việc này viết được bằng recursive common table expression (WITH RECURSIVE), nhưng cú pháp rất vụng. Ngoài ra còn phải lo vòng lặp trong graph, và chọn duyệt theo chiều rộng hay chiều sâu. Tin tốt là chuẩn SQL đang thêm ngôn ngữ truy vấn graph GQL, lấy cảm hứng từ Cypher, GSQL và PGQL.

Thực tế

Cùng một câu hỏi: 4 dòng Cypher, 31 dòng SQL. Đây là ví dụ rõ nhất trong chương cho câu của Wittgenstein: ngôn ngữ giới hạn những gì ta dễ dàng diễn đạt.

3.13 · Triple-Stores and SPARQL

Mọi thứ là bộ ba (chủ ngữ, vị ngữ, tân ngữ) Triple-Stores and SPARQL

Tóm tắt

  • Triple-store lưu mọi thông tin dưới dạng (subject, predicate, object), ví dụ (Jim, likes, bananas). Về khả năng diễn đạt, nó gần như tương đương property graph.
  • Nếu object là giá trị (chuỗi, số), triple là một thuộc tính. Nếu object là một đỉnh khác, triple là một cạnh.
  • SPARQL là ngôn ngữ truy vấn cho RDF. Cypher mượn cách so khớp mẫu từ SPARQL nên hai ngôn ngữ trông rất giống nhau.

Trong triple-store (Datomic, AllegroGraph, Blazegraph…), subject tương đương một đỉnh. Object là một trong hai thứ:

  1. Một giá trị kiểu nguyên thuỷ. Khi đó predicate và object là key và value của một thuộc tính: (lucy, birthYear, 1989) giống đỉnh lucy có {"birthYear": 1989}.
  2. Một đỉnh khác. Khi đó predicate là cạnh, subject là đỉnh đuôi, object là đỉnh đầu: (lucy, marriedTo, alain).

Nói chính xác, các hệ này thường lưu thêm metadata: Amazon Neptune dùng quad (thêm graph ID), Datomic dùng bộ 5 (thêm transaction ID và cờ xoá). Định dạng Turtle viết triple khá dễ đọc. Đỉnh viết là _:tên, chỉ có nghĩa trong file đó. Dấu chấm phẩy cho phép nói nhiều điều về cùng một subject:

@prefix : <urn:example:>.
_:lucy     a :Person;   :name "Lucy";          :bornIn _:idaho.
_:idaho    a :Location; :name "Idaho";         :type "state";     :within _:usa.
_:usa      a :Location; :name "United States"; :type "country";   :within _:namerica.
_:namerica a :Location; :name "North America"; :type "continent".

Semantic Web và RDF

Nhiều công sức nghiên cứu triple-store đến từ Semantic Web, nỗ lực đầu những năm 2000 nhằm công bố dữ liệu trên web theo định dạng máy đọc được. Tầm nhìn ban đầu không thành, nhưng di sản còn lại: JSON-LD, ontology trong y sinh, Open Graph protocol của Facebook (dùng để hiện preview link), Wikidata, schema.org. Turtle thực ra là một cách mã hoá dữ liệu RDF (Resource Description Framework). Vì được thiết kế để trao đổi dữ liệu toàn Internet, subject/predicate/object thường là URI như <http://my-company.com/namespace#within>. Như vậy dữ liệu của bạn trộn với dữ liệu người khác mà không xung đột nghĩa của từ within. URI không cần truy cập được, nó chỉ là namespace.

SPARQL

SPARQL (đọc là “sparkle”) ra đời trước Cypher. Cùng truy vấn người di cư từ Mỹ sang châu Âu:

PREFIX : <urn:example:>
SELECT ?personName WHERE {
  ?person :name ?personName.
  ?person :bornIn  / :within* / :name "United States".
  ?person :livesIn / :within* / :name "Europe".
}

Hai biểu thức sau tương đương: (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location) trong Cypher và ?person :bornIn / :within* ?location. trong SPARQL. Vì RDF không phân biệt thuộc tính và cạnh (đều là predicate), cùng cú pháp đó dùng được để so khớp thuộc tính.

Ghi nhớ

Kể cả khi không quan tâm Semantic Web, triple vẫn có thể là mô hình dữ liệu nội bộ tốt: đơn giản, đồng nhất, và mọi thứ (thuộc tính lẫn quan hệ) đều truy vấn bằng một cú pháp.

3.14 · Datalog: Recursive Relational Queries

Datalog: dựng truy vấn từng luật một Datalog: Recursive Relational Queries

Tóm tắt

  • Datalog ra đời từ nghiên cứu học thuật thập niên 1980, là tập con của Prolog, dựa trên mô hình quan hệ.
  • Dữ liệu là các fact (mỗi fact là một hàng). Truy vấn là các rule suy ra bảng ảo mới, giống view trong SQL.
  • Rule có thể gọi lại chính nó (đệ quy), nên duyệt graph rất tự nhiên.

Datalog ít được kỹ sư biết tới và ít database chính thống hỗ trợ, nhưng sách cho rằng nó đáng được biết nhiều hơn vì rất mạnh với truy vấn phức tạp. Datomic, LogicBlox, CozoDB và LIquid của LinkedIn dùng Datalog.

Fact location(2, "United States", "country") nghĩa là bảng location có một hàng với ID 2, tên “United States”, loại “country”. Cạnh của graph là bảng nối hai cột: “Lucy sinh ở Idaho” là born_in(100, 3).

location(1, "North America", "continent").
location(2, "United States", "country").
location(3, "Idaho", "state").

within(2, 1).    /* US is in North America */
within(3, 2).    /* Idaho is in the US     */

person(100, "Lucy").
born_in(100, 3). /* Lucy was born in Idaho */

Cypher và SPARQL nhảy thẳng vào SELECT, còn Datalog đi từng bước nhỏ. Mỗi rule có dạng đầu :- thân. Phần trước :- định nghĩa tên và cột của bảng ảo; phần sau là các mẫu cần tìm trong bảng. Rule áp dụng khi tìm được khớp cho mọi mẫu ở vế phải, và khi đó vế trái (đã thay biến bằng giá trị) coi như được thêm vào database.

within_recursive(LocID, PlaceName) :- location(LocID, PlaceName, _). /* Rule 1 */

within_recursive(LocID, PlaceName) :- within(LocID, ViaID),         /* Rule 2 */
                                      within_recursive(ViaID, PlaceName).

migrated(PName, BornIn, LivingIn)  :- person(PersonID, PName),        /* Rule 3 */
                                      born_in(PersonID, BornID),
                                      within_recursive(BornID, BornIn),
                                      lives_in(PersonID, LivingID),
                                      within_recursive(LivingID, LivingIn).

us_to_europe(Person) :- migrated(Person, "United States", "Europe"). /* Rule 4 */
/* us_to_europe contains the row "Lucy". */

Rule 1 nói: mọi địa điểm đều “nằm trong” chính nó. Rule 2 nói: nếu A nằm trực tiếp trong B, và B nằm (đệ quy) trong P, thì A nằm trong P. Lặp lại hai rule này, bảng within_recursive cho biết mọi địa điểm nằm trong Bắc Mỹ, hay trong bất kỳ địa điểm nào khác. Rule 3 tìm người sinh ở đâu đó và sống ở đâu đó. Rule 4 gọi Rule 3 với BornIn = “United States” và LivingIn = “Europe”.

Ghi nhớ

Datalog đòi một kiểu suy nghĩ khác: chia truy vấn phức tạp thành các rule tham chiếu lẫn nhau, như chia code thành các hàm gọi nhau. Hàm đệ quy được thì rule cũng đệ quy được.

3.15 · GraphQL

GraphQL: client hỏi đúng thứ mình cần hiển thị GraphQL

Tóm tắt

  • GraphQL cho phép frontend (app di động, web) yêu cầu một JSON có đúng cấu trúc và đúng các trường cần để render UI.
  • Nó cố tình hạn chế: không có truy vấn đệ quy, không có điều kiện tìm kiếm tuỳ ý, vì truy vấn đến từ client không tin cậy.
  • Response lặp dữ liệu (tên người gửi trên mỗi tin nhắn) để UI dễ render. Server vẫn có thể lưu dạng chuẩn hoá và tự join. GraphQL chạy được trên bất kỳ loại database nào.

Lợi ích chính: lập trình viên đổi truy vấn trong code client mà không phải đổi API phía server. Cái giá: tổ chức thường cần công cụ chuyển truy vấn GraphQL thành lời gọi tới dịch vụ nội bộ (thường là REST hoặc gRPC), và phải lo phân quyền, giới hạn tần suất, hiệu năng.

Vì truy vấn có thể đến từ nguồn không tin cậy, ngôn ngữ không cho phép gì có thể đắt khi thực thi. Nếu không, người dùng có thể tấn công từ chối dịch vụ bằng cách chạy nhiều truy vấn đắt. Đặc biệt, GraphQL không có truy vấn đệ quy (khác Cypher, SPARQL, SQL, Datalog) và không cho điều kiện tìm kiếm tuỳ ý như “người sinh ở Mỹ đang sống ở châu Âu”, trừ khi chủ dịch vụ chủ động cung cấp.

Ví dụ của sách là một ứng dụng chat nhóm kiểu Discord hay Slack: lấy mọi kênh người dùng truy cập được, tên kênh và 50 tin nhắn gần nhất; mỗi tin có timestamp, nội dung, tên và ảnh người gửi; nếu tin là trả lời thì lấy thêm nội dung và tên người gửi của tin gốc. Response phản chiếu đúng cấu trúc truy vấn, không thừa, không thiếu.

Tên và ảnh người gửi được nhúng thẳng vào từng tin nhắn, lặp lại nếu một người gửi nhiều tin. replyTo cũng chép lại nội dung tin gốc. Trả về ID thì gọn hơn, nhưng client phải hỏi thêm nếu tin gốc không nằm trong 50 tin vừa lấy. GraphQL chủ động chấp nhận response lớn hơn để UI đơn giản hơn.

Cạm bẫy

Có chữ “graph” trong tên và response trông giống document, nhưng GraphQL không phải graph database hay document database. Nó là ngôn ngữ cho API, và client chỉ yêu cầu được những join mà schema GraphQL cho phép.

3.16 · Event Sourcing and CQRS

Ghi một dạng, đọc nhiều dạng Event Sourcing and CQRS

Tóm tắt

  • Ghi dữ liệu dưới dạng log sự kiện bất biến, chỉ nối thêm. Đó là cách ghi đơn giản, nhanh và giàu thông tin nhất.
  • Từ log, dựng nhiều materialized view tối ưu cho từng kiểu đọc. Dùng sự kiện làm nguồn sự thật gọi là event sourcing; tách mô hình ghi và mô hình đọc gọi là CQRS.
  • Lợi: rõ ý định, view dựng lại được, thêm view mới dễ, sửa sai dễ, có sẵn audit log. Hại: dữ liệu bên ngoài làm mất tính tất định, khó xoá dữ liệu cá nhân, tác dụng phụ khi chạy lại.

Ở mọi mô hình trước, dữ liệu được đọc theo đúng dạng nó được ghi. Trong ứng dụng phức tạp, khó tìm một dạng thoả mọi cách đọc. Nếu đằng nào cũng dẫn xuất dạng này từ dạng kia (như ETL ở Chương 1), sao không chọn hẳn một dạng tối ưu cho ghi và các dạng khác tối ưu cho đọc?

Dạng ghi đơn giản nhất là event log: mỗi lần ghi, mã hoá dữ liệu thành một chuỗi tự chứa (có thể là JSON) kèm timestamp, rồi nối vào cuối dãy sự kiện. Sự kiện bất biến: không sửa, không xoá, chỉ nối thêm sự kiện mới (có thể thay thế ý nghĩa của sự kiện cũ).

Ví dụ trong sách (Hình 3-8) là hệ thống quản lý hội nghị. Người tham dự tự đăng ký và trả bằng thẻ; công ty mua chỗ số lượng lớn, trả bằng hoá đơn rồi gán chỗ cho từng người; một số chỗ giữ cho diễn giả, nhà tài trợ, tình nguyện viên; đặt chỗ có thể bị huỷ; ban tổ chức có thể đổi sang phòng khác làm thay đổi sức chứa. Chỉ riêng việc tính “còn bao nhiêu chỗ” đã thành truy vấn khó.

Mỗi thay đổi trạng thái được lưu thành một sự kiện. Mỗi khi log có sự kiện mới, các materialized view (còn gọi là projection hay read model) được cập nhật: một view cho trạng thái từng booking, một view vẽ biểu đồ cho dashboard ban tổ chức, một view sinh file cho máy in thẻ đeo. Dùng sự kiện làm nguồn sự thật là event sourcing. Duy trì các dạng đọc riêng, dẫn xuất từ dạng ghi, là CQRS (command query responsibility segregation). Hai thuật ngữ xuất phát từ cộng đồng domain-driven design.

Command và event

Yêu cầu từ người dùng là một command, phải được kiểm tra trước. Chỉ khi command hợp lệ (ví dụ còn đủ chỗ), nó mới trở thành một sự thật và sự kiện tương ứng được thêm vào log. Vì vậy log chỉ chứa sự kiện hợp lệ, và view không được phép từ chối sự kiện. Nên đặt tên sự kiện ở thì quá khứ (“chỗ đã được đặt”), vì sự kiện ghi lại điều đã xảy ra. Dù người dùng sau đó huỷ, việc họ từng giữ chỗ vẫn đúng; việc huỷ là một sự kiện riêng.

Event sourcing giống bảng fact của star schema ở chỗ cả hai là tập sự kiện trong quá khứ. Khác ở chỗ các hàng fact có cùng cột, còn sự kiện có nhiều loại với thuộc tính khác nhau. Và bảng fact không có thứ tự, còn với event sourcing thì thứ tự là quan trọng: đặt chỗ rồi huỷ, xử lý ngược thứ tự là vô nghĩa.

Ưu điểm

  • Sự kiện truyền đạt ý định. “Booking đã bị huỷ” dễ hiểu hơn nhiều so với “cột active ở hàng 4001 thành false, ba hàng ở seat_assignments bị xoá, một hàng hoàn tiền được thêm vào payments”.
  • View được dẫn xuất tái lập được: xoá view rồi xử lý lại cùng sự kiện, cùng thứ tự, cùng code sẽ ra cùng kết quả. Có bug trong code duy trì view thì sửa code rồi dựng lại.
  • Có thể có nhiều view, mỗi view tối ưu cho một truy vấn, dùng mô hình bất kỳ, phi chuẩn hoá thoải mái, thậm chí chỉ giữ trong bộ nhớ.
  • Muốn trình bày thông tin theo cách mới thì dựng view mới từ log có sẵn. Thêm loại sự kiện, thêm thuộc tính, hay gắn hành vi mới vào sự kiện cũ (ai huỷ thì mời người kế tiếp trong danh sách chờ).
  • Sự kiện ghi nhầm có thể xoá rồi dựng lại view. Event sourcing giảm số hành động không đảo ngược được.
  • Log là audit log đầy đủ, có giá trị trong ngành bị quản lý chặt.

Nhược điểm

  • Cẩn thận với thông tin bên ngoài. Nếu view cần đổi tiền tệ theo tỷ giá lấy lúc xử lý, dựng lại vào ngày khác sẽ ra kết quả khác. Phải đưa tỷ giá vào sự kiện, hoặc tra tỷ giá lịch sử theo timestamp của sự kiện.
  • Sự kiện bất biến gây khó khi người dùng yêu cầu xoá dữ liệu cá nhân (GDPR). Log theo từng người thì xoá cả log; log chung nhiều người thì phải lưu dữ liệu cá nhân bên ngoài sự kiện hoặc mã hoá bằng khoá có thể huỷ, và dựng lại view sẽ khó hơn.
  • Chạy lại sự kiện cần cẩn thận với tác dụng phụ ra bên ngoài: bạn không muốn gửi lại email xác nhận mỗi lần dựng lại view.

Có thể làm event sourcing trên bất kỳ database nào. Cũng có hệ chuyên dụng như EventStoreDB, MartenDB (trên PostgreSQL), Axon Framework, hoặc dùng Apache Kafka lưu log và stream processor cập nhật view. Yêu cầu duy nhất quan trọng: mọi view phải xử lý sự kiện đúng theo thứ tự trong log. Trong hệ phân tán, điều này không dễ.

Ghi nhớ

Log là hệ thống ghi gốc (system of record). Mọi view chỉ là dữ liệu dẫn xuất: xoá đi dựng lại được. Đây là cùng ý tưởng “system of record và derived data” ở Chương 1, đẩy đến tận cùng.

3.17 · Dataframes, Matrices, and Arrays

Dataframe: cầu nối từ bảng sang ma trận Dataframes, Matrices, and Arrays

Tóm tắt

  • Dataframe (R, pandas, Spark, Dask…) trông giống bảng, có các thao tác giống quan hệ (lọc, nhóm, tổng hợp, merge thay cho join), nhưng thường được thao tác bằng chuỗi lệnh từng bước.
  • Ứng dụng phổ biến: chuyển dữ liệu dạng quan hệ thành ma trận số mà thuật toán machine learning cần.
  • Dữ liệu không phải số được mã hoá thành số, ví dụ one-hot encoding cho cột phân loại.

Dataframe hiếm gặp trong OLTP nhưng phổ biến với data scientist, dùng để chuẩn bị dữ liệu huấn luyện, khám phá, phân tích thống kê, trực quan hoá. Thay vì một truy vấn khai báo như SQL, dataframe thường được biến đổi qua một chuỗi lệnh, hợp với cách data scientist “nhào nặn” (wrangle) dữ liệu dần dần trên bản sao riêng, thường ở máy của mình.

Hình 3-9 trong sách: bên trái là bảng quan hệ ghi người dùng chấm phim (1–5 sao); bên phải là ma trận, mỗi cột là một phim, mỗi hàng là một người, giống pivot table trong spreadsheet. Ma trận này thưa: nhiều cặp người–phim không có dữ liệu, và điều đó không sao. Ma trận có thể có hàng nghìn cột nên không hợp với database quan hệ, nhưng dataframe và thư viện mảng thưa (như NumPy) xử lý dễ dàng.

Ma trận chỉ chứa số. Ngày tháng có thể được co giãn thành số thực trong một khoảng. Cột chỉ nhận một trong vài giá trị cố định (thể loại phim) thường dùng one-hot encoding: mỗi giá trị một cột, đặt 1 ở cột đúng và 0 ở cột khác. Cách này dễ mở rộng cho phim thuộc nhiều thể loại. Khi đã là ma trận số, dữ liệu sẵn sàng cho đại số tuyến tính, nền tảng của nhiều thuật toán machine learning, ví dụ hệ thống gợi ý phim.

Cũng có array database như TileDB, chuyên lưu mảng số nhiều chiều lớn: dữ liệu địa không gian dạng lưới, ảnh y khoa, quan sát thiên văn. Ngành tài chính cũng dùng dataframe cho chuỗi thời gian như giá tài sản và giao dịch.

Thực tế

Hệ thống gợi ý thật có hàng triệu người dùng và hàng chục nghìn phim, nên ma trận thường trống hơn 99%. Lưu dạng thưa (chỉ lưu ô có giá trị) là bắt buộc.

3.★ · Summary

Tổng kết chương 3 Summary & quiz

Tóm tắt

  • Không mô hình nào tốt nhất. Mỗi mô hình làm một số truy vấn dễ và số khác vụng về.
  • Mô hình này có thể giả lập mô hình kia (graph trong bảng quan hệ), nhưng kết quả thường vụng, như SQL đệ quy so với Cypher.
  • Database đang mở rộng sang “lãnh thổ” của nhau: JSON trong SQL, join trong document DB, graph trong chuẩn SQL.

Mô hình quan hệ đã hơn nửa thế kỷ tuổi nhưng vẫn quan trọng, nhất là trong kho dữ liệu và phân tích kinh doanh, nơi star/snowflake schema và SQL có mặt khắp nơi. Các lựa chọn khác phổ biến ở những lĩnh vực khác:

  • Document nhắm tới dữ liệu đến dưới dạng JSON tự chứa, ít quan hệ giữa document này với document khác.
  • Graph đi theo hướng ngược lại: mọi thứ đều có thể liên quan tới mọi thứ, truy vấn phải đi nhiều bước (Cypher, SPARQL, Datalog có truy vấn đệ quy).
  • Dataframe tổng quát hoá dữ liệu quan hệ sang rất nhiều cột, làm cầu nối giữa database và mảng nhiều chiều của machine learning, thống kê, tính toán khoa học.
  • Event sourcing biểu diễn dữ liệu bằng log sự kiện bất biến chỉ nối thêm, tốt cho ghi và cho miền nghiệp vụ phức tạp. Để đọc hiệu quả, log được dịch sang view tối ưu cho đọc qua CQRS.

Điểm chung của các mô hình phi quan hệ: thường không ép schema. Nhưng ứng dụng vẫn giả định dữ liệu có cấu trúc. Câu hỏi chỉ là schema tường minh (ép khi ghi) hay ngầm định (giả định khi đọc).

Sách cũng nhắc vài mô hình chưa bàn: dữ liệu genome cần tìm kiếm chuỗi tương tự (một chuỗi DNA rất dài so với kho chuỗi gần giống), sổ cái tài chính kiểu kế toán kép, và tìm kiếm toàn văn (full-text search) thường dùng cùng database. Chương 4 sẽ chuyển sang cách các mô hình này được hiện thực trong storage engine.

Kiểm tra nhanh

Lợi ích quan trọng nhất của ngôn ngữ truy vấn khai báo theo sách là gì?

  1. Luôn chạy nhanh hơn code viết tay
  2. Không cần index
  3. Database có thể đổi cách thực thi (index, song song) mà không phải sửa truy vấn
  4. Không cần schema

Truy vấn khai báo giấu chi tiết thực thi, nên bộ tối ưu tự chọn index, thuật toán join, chạy song song. Nó không tự động nhanh hơn mọi code viết tay, và vẫn cần index để nhanh.

Hồ sơ LinkedIn (vị trí, học vấn, liên lạc) hợp với document model chủ yếu vì:

  1. Có nhiều quan hệ nhiều-nhiều
  2. Là cây quan hệ một-nhiều và thường được tải cả cây một lúc
  3. Cần truy vấn đệ quy
  4. Không bao giờ thay đổi

Cấu trúc cây một-nhiều cộng với nhu cầu đọc cả hồ sơ khiến locality của document phát huy tác dụng. Nhiều-nhiều thì nghiêng về quan hệ; đệ quy thì nghiêng về graph.

Bạn lưu tên vùng trực tiếp trong mỗi hồ sơ (phi chuẩn hoá). Khi thành phố đổi tên, điều gì xảy ra?

  1. Phải sửa mọi bản sao, và nếu crash giữa chừng dữ liệu có thể lệch nhau
  2. Chỉ cần sửa một chỗ
  3. Database tự cập nhật nhờ foreign key
  4. Không ảnh hưởng gì vì đọc nhanh hơn

Phi chuẩn hoá nhân bản thông tin có nghĩa với con người. Đổi nó tốn nhiều lượt ghi và có nguy cơ bất nhất nếu không có transaction nguyên tử trên nhiều document.

Vì sao timeline của X chỉ lưu ID bài đăng và ID người đăng?

  1. Vì không thể join ở quy mô lớn
  2. Vì ID nén tốt hơn
  3. Vì follower không cần xem nội dung
  4. Vì số like, username, ảnh đại diện đổi liên tục và timeline phải hiện bản mới nhất; chép vào còn tăng chi phí lưu trữ

Dữ liệu hay đổi được giữ chuẩn hoá và hydrate lúc đọc. Hydrate song song hoá tốt và không phụ thuộc số follower, nên join lúc đọc không cản khả năng mở rộng.

“Schemaless” chính xác hơn nên gọi là gì?

  1. Schema-on-write
  2. Schema-on-read: schema ngầm định trong code đọc, chỉ được diễn giải khi đọc
  3. Không có schema nào cả
  4. Snowflake schema

Code đọc dữ liệu luôn giả định một cấu trúc. Khác biệt chỉ là database có kiểm tra lúc ghi hay không.

Vì sao truy vấn “sinh ở Mỹ, sống ở châu Âu” khó viết bằng SQL thường?

  1. SQL không join được
  2. SQL không có kiểu JSON
  3. Số cạnh WITHIN phải đi qua không biết trước, nên số join không cố định; phải dùng WITH RECURSIVE
  4. SQL không có index

Nơi sinh có thể là thành phố, bang, hay quốc gia. Cypher diễn đạt bằng WITHIN*0..; SQL cần recursive CTE dài 31 dòng.

Trong event sourcing, khi nào một command trở thành event trong log?

  1. Sau khi được kiểm tra là hợp lệ, ví dụ còn đủ chỗ
  2. Ngay khi người dùng bấm nút
  3. Khi materialized view chấp nhận nó
  4. Khi được ghi vào bảng fact

Command được validate trước. Chỉ command hợp lệ mới thành sự thật và được nối vào log. View không được phép từ chối sự kiện.

Nhược điểm nào sau đây là của event sourcing?

  1. Không thể có nhiều view
  2. Không có audit log
  3. Khó thêm loại sự kiện mới
  4. Dựng lại view có thể gửi lại email, và tra tỷ giá bên ngoài lúc xử lý làm kết quả không tất định

Tác dụng phụ bên ngoài và dữ liệu bên ngoài là hai cạm bẫy chính, cộng với khó xoá dữ liệu cá nhân trong log bất biến. Ba lựa chọn còn lại thực ra là ưu điểm.
