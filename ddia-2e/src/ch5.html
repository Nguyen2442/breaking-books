Encoding and Evolution Mã hoá và tiến hoá dữ liệu

Everything changes and nothing stands still.— Heraclitus of Ephesus, as quoted by Plato in Cratylus (360 BCE)

Ứng dụng luôn thay đổi, và dữ liệu nó lưu cũng phải thay đổi theo. Nhưng code mới không thể thay code cũ ở mọi nơi trong cùng một tích tắc, nên dữ liệu cũ, dữ liệu mới, code cũ và code mới phải sống chung. Chương này mổ xẻ các định dạng mã hoá (JSON, Thrift, Protocol Buffers, Avro…) đến từng byte để thấy cái nào giúp hệ thống tiến hoá an toàn, rồi xem dữ liệu chảy giữa các tiến trình theo ba ngả: database, lời gọi dịch vụ và hàng đợi thông điệp.

5.1 · Introduction

Tương thích ngược, tương thích xuôi và nâng cấp cuốn chiếu Backward/Forward Compatibility and Rolling Upgrades

Tóm tắt

  • Đổi tính năng thường kéo theo đổi dữ liệu: thêm trường, thêm loại bản ghi, trình bày dữ liệu cũ theo cách mới.
  • Code không đổi tức thời được: phía server ta nâng cấp cuốn chiếu từng vài node một; phía client thì tuỳ người dùng có chịu cập nhật hay không.
  • Vì vậy code cũ, code mới, dữ liệu cũ, dữ liệu mới cùng tồn tại. Cần tương thích ngược (code mới đọc được dữ liệu cũ) và tương thích xuôi (code cũ đọc được dữ liệu mới).

Ở Chương 2 ta đã gặp khái niệm khả năng tiến hoá (evolvability): hệ thống tốt là hệ thống dễ thay đổi. Chương này nhìn vấn đề đó từ phía dữ liệu. Database quan hệ giả định cả bảng tuân theo đúng một schema tại mỗi thời điểm (đổi bằng ALTER TABLE). Database “không schema” (schema-on-read, xem Chương 3) thì chứa lẫn lộn bản ghi định dạng cũ và mới. Dù kiểu nào, khi định dạng dữ liệu đổi thì code đọc/ghi nó cũng phải đổi theo.

Vấn đề là trong một hệ thống lớn, việc đổi code không xảy ra cùng lúc ở mọi nơi:

  • Phía server, ta thường triển khai phiên bản mới lên vài node, theo dõi xem có ổn không, rồi mới lan dần ra các node còn lại. Cách này (rolling upgrade hay staged rollout) giúp deploy mà không cần dừng dịch vụ, nên đội ngũ dám release thường xuyên hơn.
  • Phía client (app di động, app desktop), ta phụ thuộc vào người dùng: có người vài tháng sau mới cập nhật.

Hệ quả: ở một thời điểm, có node chạy code mới đọc bản ghi do code cũ ghi, và có node chạy code cũ đọc bản ghi do code mới ghi. Hai yêu cầu tương thích tương ứng:

  • Tương thích ngược (backward compatibility): code mới đọc được dữ liệu do code cũ ghi. Thường dễ: khi viết code mới, bạn biết rõ định dạng cũ và có thể xử lý nó một cách tường minh.
  • Tương thích xuôi (forward compatibility): code cũ đọc được dữ liệu do code mới ghi. Khó hơn, vì code cũ được viết trước khi định dạng mới ra đời, nên nó phải biết lờ đi những thứ nó không hiểu.

Thử kéo thanh trượt dưới đây để xem trong lúc nâng cấp cuốn chiếu, ô nào của ma trận “code × dữ liệu” thực sự xuất hiện, và nếu thiếu một chiều tương thích thì bao nhiêu phần trăm lượt đọc sẽ hỏng.

Ghi nhớ

“Ngược” và “xuôi” được đặt tên theo góc nhìn của code: ngược = code mới nhìn về dữ liệu quá khứ; xuôi = code cũ nhìn tới dữ liệu tương lai. Trong lúc rolling upgrade, bạn cần cả hai.

5.2 · Formats for Encoding Data · Language-Specific Formats

Mã hoá là gì, và vì sao đừng dùng định dạng riêng của ngôn ngữ Encoding and Language-Specific Formats

Tóm tắt

  • Trong bộ nhớ, dữ liệu là object, struct, hash table… nối với nhau bằng con trỏ. Ra file hay ra mạng, nó phải thành một chuỗi byte tự chứa. Chuyển từ dạng thứ nhất sang dạng thứ hai là mã hoá, chiều ngược lại là giải mã.
  • java.io.Serializable, pickle của Python, Marshal của Ruby rất tiện nhưng có bốn vấn đề sâu: trói bạn vào một ngôn ngữ, lỗ hổng bảo mật khi giải mã dữ liệu lạ, gần như bỏ qua việc tương thích phiên bản, và thường kém hiệu quả.
  • Chỉ nên dùng chúng cho mục đích rất tạm thời.

Chương trình làm việc với dữ liệu ở ít nhất hai dạng. Trong bộ nhớ, dữ liệu nằm trong các cấu trúc tối ưu cho CPU truy cập, thường đầy con trỏ. Nhưng một con trỏ (địa chỉ ô nhớ) chẳng có nghĩa gì với tiến trình khác hay với chính bạn sau khi khởi động lại. Vì thế khi ghi ra đĩa hoặc gửi qua mạng, dữ liệu phải được chuyển thành một chuỗi byte tự đứng được, ví dụ một tài liệu JSON.

Việc chuyển này có nhiều tên: encoding, serialization, marshalling; chiều ngược lại là decoding, parsing, deserialization, unmarshalling. Sách chọn chữ encoding, vì serialization còn có một nghĩa hoàn toàn khác trong ngữ cảnh transaction (xem Chương 8). Cũng lưu ý: mã hoá (encoding) ở đây không liên quan gì đến mã hoá bảo mật (encryption).

Định dạng gắn với ngôn ngữ

Nhiều ngôn ngữ có sẵn cơ chế biến object trong bộ nhớ thành byte: Java có java.io.Serializable, Ruby có Marshal, Python có pickle, ngoài ra có thư viện bên thứ ba như Kryo cho Java. Chỉ một dòng code là lưu và khôi phục được cả một object graph. Nhưng cái giá phải trả:

  1. Trói vào một ngôn ngữ. Dữ liệu pickle gần như không đọc được từ Java hay Go. Lưu trữ hoặc truyền dữ liệu bằng định dạng này nghĩa là cam kết dùng ngôn ngữ hiện tại rất lâu, và khó tích hợp với hệ thống của tổ chức khác.
  2. Bảo mật. Để khôi phục đúng kiểu object, bộ giải mã phải có khả năng khởi tạo bất kỳ class nào. Nếu kẻ tấn công đưa được chuỗi byte tuỳ ý vào bộ giải mã, họ có thể khởi tạo class tuỳ ý, và thường từ đó chạy được code tuỳ ý trên máy bạn (giải mã dữ liệu không tin cậy).
  3. Phiên bản là chuyện phụ. Các thư viện này nhắm tới sự tiện lợi, nên tương thích ngược/xuôi thường bị bỏ quên.
  4. Hiệu năng cũng là chuyện phụ. Serialization có sẵn của Java nổi tiếng chậm và cồng kềnh.
Cạm bẫy

Đừng bao giờ pickle.loads hay ObjectInputStream.readObject dữ liệu đến từ mạng hoặc từ người dùng. Lỗ hổng deserialization từng ảnh hưởng WebLogic, WebSphere, JBoss, Jenkins (2015) và Ruby on Rails (2013), đúng như các tài liệu tham khảo của sách.

5.3 · JSON, XML, and Binary Variants

JSON, XML, CSV và những cái bẫy tinh vi JSON, XML, CSV and Their Subtle Problems

Tóm tắt

  • JSON, XML, CSV là định dạng văn bản, độc lập ngôn ngữ, ai cũng đọc được. Chúng phổ biến nhất cho việc trao đổi dữ liệu giữa các tổ chức.
  • Nhưng chúng mơ hồ về số: XML/CSV không phân biệt số với chuỗi chữ số; JSON không phân biệt số nguyên với số thực và không quy định độ chính xác, nên số nguyên lớn hơn 253 bị sai khi JavaScript đọc.
  • Chúng không hỗ trợ chuỗi nhị phân; người ta phải bọc byte trong Base64, làm dữ liệu to thêm 33%.
  • Schema cho XML/JSON có nhưng phức tạp; CSV không có schema và quy tắc escape thì mỗi parser hiểu một kiểu.

Khi cần một định dạng mà nhiều ngôn ngữ cùng đọc được, ứng viên hiển nhiên là JSON và XML: được biết đến rộng rãi, hỗ trợ rộng rãi và, theo lời tác giả, bị ghét cũng rộng rãi gần bằng. XML bị chê dài dòng và phức tạp không cần thiết. JSON thắng nhờ có sẵn trong trình duyệt (vì là tập con của JavaScript) và đơn giản hơn XML. CSV cũng phổ biến, dù kém biểu đạt hơn. Ngoài chuyện cú pháp, chúng có mấy vấn đề tinh vi hơn:

  • Số. Trong XML và CSV, 01234 là số hay chuỗi? Không có schema bên ngoài thì không biết. JSON phân biệt chuỗi với số, nhưng không phân biệt số nguyên với số thực và không nói gì về độ chính xác. Ngôn ngữ dùng số thực dấu phẩy động IEEE 754 (như JavaScript) chỉ biểu diễn chính xác số nguyên đến 253. Twitter dùng số 64-bit làm ID tweet, nên API của họ trả ID hai lần: một lần là số JSON, một lần là chuỗi thập phân, để app JavaScript không đọc sai.
  • Chuỗi nhị phân. JSON và XML hỗ trợ tốt chuỗi Unicode, nhưng không có kiểu cho chuỗi byte thô. Cách lách quen thuộc là Base64: chạy được, nhưng hơi “hack” và tăng kích thước 33%.
  • Schema. XML Schema và JSON Schema đều mạnh, và vì thế khó học, khó cài đặt. XML Schema được dùng khá nhiều; nhiều công cụ JSON thì bỏ qua schema, nên logic “trường này là số hay Base64” bị hardcode trong ứng dụng.
  • CSV không có schema; ý nghĩa mỗi cột do ứng dụng tự quy ước. Thêm một cột là phải sửa tay. Giá trị chứa dấu phẩy hay xuống dòng thì sao? Quy tắc escape đã được chuẩn hoá (RFC 4180), nhưng không phải parser nào cũng làm đúng.

Dù vậy, với dữ liệu trao đổi giữa các tổ chức, ba định dạng này “đủ tốt” và sẽ còn phổ biến. Làm cho các tổ chức khác nhau đồng ý với nhau về bất cứ thứ gì đã khó hơn nhiều so với chuyện định dạng đẹp hay hiệu quả.

Thực tế

Khi API của bạn trả về ID 64-bit (Snowflake ID, ID của Discord, Twitter/X, nhiều hệ thống đơn hàng), hãy trả chúng dưới dạng chuỗi trong JSON, hoặc trả cả hai như Twitter từng làm (id và id_str).

5.4 · Binary encoding

Mã hoá nhị phân cho JSON: MessagePack Binary Encoding: MessagePack

Tóm tắt

  • Với dữ liệu chỉ dùng nội bộ, bạn có thể chọn định dạng gọn hơn và parse nhanh hơn JSON. Với vài MB thì không đáng; với hàng terabyte thì đáng.
  • Có cả một rừng “JSON nhị phân”: MessagePack, BSON, BJSON, UBJSON, BISON, Smile… Chúng giữ nguyên mô hình dữ liệu của JSON và không có schema, nên vẫn phải nhét tên trường vào mỗi bản ghi.
  • Bản ghi ví dụ của sách: JSON (bỏ khoảng trắng) 81 byte, MessagePack 66 byte. Tiết kiệm chút ít, đổi lại mất khả năng đọc bằng mắt.

Suốt phần còn lại của mục mã hoá, sách dùng một bản ghi duy nhất làm ví dụ và mã hoá nó bằng nhiều định dạng:

{
  "userName": "Martin",
  "favoriteNumber": 1337,
  "interests": ["daydreaming", "hacking"]
}

Với MessagePack, byte đầu tiên 0x83 cho biết đây là một object (4 bit cao là 0x80) có 3 trường (4 bit thấp là 0x03). Byte tiếp theo 0xa8 nghĩa là “một chuỗi (0xa0) dài 8 byte”, theo sau là 8 byte ASCII userName. Vì độ dài đã biết trước, không cần ký tự kết thúc hay escape gì cả. Tiếp đó 0xa6 + Martin, và cứ thế.

Bộ mã hoá dưới đây được cài đặt thật bằng JavaScript cho sáu định dạng của chương. Bản ghi mặc định là ví dụ của sách nên kích thước khớp với sách: JSON 81, MessagePack 66, Thrift BinaryProtocol 59, Thrift CompactProtocol 34, Protocol Buffers 33, Avro 32 byte. Sửa giá trị (ví dụ xoá số yêu thích, gõ tên có dấu tiếng Việt, thêm sở thích) để xem từng byte thay đổi.

Ghi nhớ

Định dạng “JSON nhị phân” chỉ nén được phần cú pháp (ngoặc, dấu nháy, chữ số), không nén được tên trường, vì không có schema thì người đọc cần tên trường để hiểu dữ liệu. Muốn gọn thật sự, phải bỏ được tên trường, và đó là việc của schema.

5.5 · Thrift and Protocol Buffers

Thrift và Protocol Buffers: thay tên trường bằng con số Thrift and Protocol Buffers

Tóm tắt

  • Apache Thrift (gốc Facebook) và Protocol Buffers (gốc Google) đều bắt buộc có schema, viết bằng một ngôn ngữ định nghĩa giao diện (IDL), rồi sinh code cho nhiều ngôn ngữ.
  • Thay vì tên trường, dữ liệu mã hoá chứa field tag: các số 1, 2, 3 trong schema.
  • Thrift BinaryProtocol: 59 byte. CompactProtocol gộp kiểu và tag vào một byte, dùng số nguyên độ dài thay đổi: 34 byte. Protocol Buffers đóng gói hơi khác: 33 byte.
  • required/optional không ảnh hưởng gì đến byte được ghi; required chỉ bật một kiểm tra lúc chạy.

Thrift và Protocol Buffers ra đời từ cùng một ý tưởng và cùng được mở mã nguồn khoảng 2007–08. Schema cho bản ghi ví dụ:

// Thrift IDL
struct Person {
  1: required string       userName,
  2: optional i64          favoriteNumber,
  3: optional list<string> interests
}

// Protocol Buffers
message Person {
    required string user_name       = 1;
    optional int64  favorite_number = 2;
    repeated string interests       = 3;
}

Công cụ sinh code đọc schema này và tạo class cho Java, C++, Go, Python… Code ứng dụng gọi class sinh ra để mã hoá/giải mã.

BinaryProtocol, CompactProtocol, Protocol Buffers

Thrift có hai định dạng nhị phân chính (thực ra có ba, cộng thêm hai định dạng JSON nữa). BinaryProtocol giống MessagePack ở chỗ mỗi trường có byte kiểu và độ dài, chuỗi vẫn là UTF-8; khác biệt lớn là không có tên trường, chỉ có tag 2 byte. Kết quả 59 byte. CompactProtocol mang cùng thông tin nhưng gộp kiểu và tag vào một byte (thực ra là độ chênh giữa tag này và tag trước) và dùng varint: số 1337 chỉ tốn 2 byte thay vì 8. Mỗi byte varint dùng bit cao nhất để báo “còn byte nữa”, nên số từ −64 đến 63 nằm gọn trong 1 byte, từ −8192 đến 8191 trong 2 byte. Protocol Buffers chỉ có một định dạng nhị phân, đóng bit hơi khác nhưng tư tưởng giống CompactProtocol: 33 byte.

Trong sách

Hình 4-2, 4-3, 4-4 của sách vẽ đúng các chuỗi byte bạn thấy ở trên. Chú ý một chi tiết: Thrift CompactProtocol mã hoá 1337 là f2 14 (có zigzag), còn Protocol Buffers mã hoá int64 là b9 0a (không zigzag; muốn zigzag phải khai báo sint64).

5.6 · Field tags and schema evolution · Datatypes and schema evolution

Field tag và tiến hoá schema Field Tags and Schema Evolution

Tóm tắt

  • Một bản ghi Thrift/Protobuf chỉ là các trường nối nhau, mỗi trường mang tag và kiểu. Trường không có giá trị thì bị bỏ qua.
  • Đổi tên trường thoải mái (dữ liệu không chứa tên). Đổi tag thì không bao giờ: mọi dữ liệu cũ thành vô nghĩa.
  • Thêm trường với tag mới: code cũ gặp tag lạ thì bỏ qua (nhờ kiểu dữ liệu mà biết phải nhảy bao nhiêu byte) → tương thích xuôi. Trường mới phải là optional hoặc có giá trị mặc định → tương thích ngược.
  • Xoá trường: chỉ xoá được trường optional, và không bao giờ dùng lại tag đó.
  • Đổi kiểu dữ liệu có thể mất chính xác (int32 ↔ int64). Protobuf cho phép đổi optional thành repeated.

Schema chắc chắn sẽ phải đổi theo thời gian; sách gọi đó là tiến hoá schema. Vì dữ liệu chỉ chứa tag, tag chính là “danh tính” của trường. Từ đó suy ra luật chơi:

  • Thêm trường mới với một tag chưa từng dùng. Code cũ đọc dữ liệu mới, thấy tag lạ, dựa vào kiểu dữ liệu để biết độ dài rồi nhảy qua: tương thích xuôi. Code mới đọc dữ liệu cũ thì thấy thiếu trường mới; nếu trường đó là required thì kiểm tra thất bại. Vì vậy mọi trường thêm sau lần triển khai đầu tiên phải là optional hoặc có giá trị mặc định.
  • Xoá trường là phép ngược của thêm, nên các mối lo về tương thích cũng đảo chiều: chỉ xoá được trường optional (trường required thì không bao giờ xoá được), và tag của nó phải được “nghỉ hưu” vĩnh viễn, vì ở đâu đó vẫn còn dữ liệu cũ mang tag ấy.

Trong phòng thí nghiệm dưới đây, mỗi phương án đổi schema được mã hoá và giải mã thật theo định dạng Protocol Buffers. Bạn sẽ thấy cả hai chiều: code mới đọc dữ liệu cũ, và code cũ đọc dữ liệu mới.

Đổi kiểu dữ liệu

Đổi kiểu của một trường đôi khi được phép (xem tài liệu của từng thư viện), nhưng có rủi ro mất chính xác hoặc bị cắt cụt. Ví dụ đổi số nguyên 32-bit thành 64-bit: code mới đọc dữ liệu cũ không sao (thiếu bit thì điền 0), nhưng code cũ vẫn dùng biến 32-bit, nên khi đọc một giá trị 64-bit không vừa 32 bit, giá trị bị cắt cụt.

Một chi tiết thú vị: Protocol Buffers không có kiểu list mà có đánh dấu repeated. Trường repeated được mã hoá đúng như tên gọi: cùng một tag xuất hiện nhiều lần. Nhờ đó đổi một trường optional (một giá trị) thành repeated (nhiều giá trị) là hợp lệ: code mới đọc dữ liệu cũ thấy list 0 hoặc 1 phần tử; code cũ đọc dữ liệu mới chỉ thấy phần tử cuối. Thrift có kiểu list riêng nên không tiến hoá kiểu này được, đổi lại hỗ trợ list lồng nhau.

Thực tế

Protobuf có từ khoá reserved để “khoá” tag và tên đã xoá, compiler sẽ báo lỗi nếu ai đó dùng lại. Proto3 bỏ hẳn required, một phần vì đúng lý do sách nêu: trường required không bao giờ xoá được.

5.7 · Avro

Avro: không tag, không kiểu, chỉ có giá trị Avro

Tóm tắt

  • Apache Avro ra đời năm 2009 trong Hadoop vì Thrift không hợp với nhu cầu của Hadoop. Nó có schema (dạng IDL cho người viết, dạng JSON cho máy đọc) nhưng schema không có số tag.
  • Bản ghi ví dụ chỉ còn 32 byte, gọn nhất trong các định dạng. Dữ liệu chỉ là các giá trị nối nhau; không có gì cho biết đâu là trường nào hay kiểu gì.
  • Hệ quả: chỉ giải mã đúng được khi biết chính xác schema mà người ghi đã dùng.

Schema của bản ghi ví dụ, viết bằng Avro IDL và bằng JSON:

record Person {
    string               userName;
    union { null, long } favoriteNumber = null;
    array<string>        interests;
}

{ "type": "record", "name": "Person",
  "fields": [
    {"name": "userName",       "type": "string"},
    {"name": "favoriteNumber", "type": ["null", "long"], "default": null},
    {"name": "interests",      "type": {"type": "array", "items": "string"}}
  ] }

Nhìn chuỗi byte Avro bạn sẽ không thấy gì định danh trường hay kiểu. Một chuỗi chỉ là tiền tố độ dài + byte UTF-8; không có gì nói rằng đó là chuỗi, nó có thể là số nguyên hay thứ khác hoàn toàn. Số nguyên dùng varint zigzag như Thrift CompactProtocol. Để parse, bộ giải mã đi qua các trường theo đúng thứ tự trong schema và dùng schema để biết kiểu của từng trường.

Ghi nhớ

Avro gọn vì đẩy toàn bộ thông tin cấu trúc ra khỏi dữ liệu và vào schema. Vậy làm sao Avro hỗ trợ tiến hoá schema? Câu trả lời ở mục tiếp theo: người đọc luôn có trong tay cả schema của người ghi.

5.8 · The writer’s schema and the reader’s schema · Schema evolution rules

Schema của người ghi và schema của người đọc Writer’s Schema and Reader’s Schema

Tóm tắt

  • Schema người ghi: phiên bản schema mà ứng dụng dùng khi mã hoá. Schema người đọc: phiên bản schema mà code đọc đang mong đợi.
  • Hai schema không cần giống nhau, chỉ cần tương thích. Thư viện Avro đặt hai schema cạnh nhau và dịch dữ liệu từ schema người ghi sang schema người đọc.
  • Trường được khớp theo tên, nên thứ tự không quan trọng. Trường người ghi có mà người đọc không có: bỏ qua. Trường người đọc cần mà người ghi không có: điền giá trị mặc định của schema người đọc.
  • Luật: chỉ được thêm hoặc xoá trường có giá trị mặc định.

Ý tưởng chính của Avro: khi mã hoá, ứng dụng dùng phiên bản schema nó biết (thường được biên dịch sẵn vào ứng dụng). Khi giải mã, nó có schema người đọc của nó, và biết schema người ghi (xem mục 5.9 để biết bằng cách nào). Đặc tả Avro định nghĩa chính xác cách đối chiếu (resolution):

  • Trường được ghép theo tên; khác thứ tự không sao.
  • Trường có trong schema người ghi nhưng không có trong schema người đọc: bị bỏ qua.
  • Trường người đọc cần nhưng schema người ghi không có: lấy giá trị mặc định khai báo trong schema người đọc. Không có mặc định thì lỗi.

Với Avro, tương thích xuôi nghĩa là schema mới làm người ghi, schema cũ làm người đọc; tương thích ngược là schema mới làm người đọc, schema cũ làm người ghi. Thêm một trường không có mặc định thì người đọc mới không đọc được dữ liệu cũ (vỡ tương thích ngược). Xoá một trường không có mặc định thì người đọc cũ không đọc được dữ liệu mới (vỡ tương thích xuôi).

Null phải được nói rõ

Trong Avro, null không phải là giá trị hợp lệ của mọi kiểu. Muốn một trường có thể null, phải dùng kiểu union, ví dụ union { null, long, string }, và chỉ dùng null làm mặc định khi nó là nhánh đầu tiên của union. Dài dòng hơn, nhưng tránh được bug vì buộc bạn nói rõ cái gì có thể null. Vì thế Avro không có optional/required; nó có union và giá trị mặc định.

Đổi kiểu được nếu Avro biết cách chuyển (ví dụ int → long). Đổi tên thì hơi khéo: schema người đọc khai báo alias cho tên cũ, nên đổi tên là tương thích ngược nhưng không tương thích xuôi. Thêm nhánh vào union cũng vậy.

Ghi nhớ

Protobuf/Thrift: danh tính trường là tag nằm trong dữ liệu. Avro: danh tính trường là tên nằm trong schema người ghi, và người đọc phải có schema đó.

5.9 · But what is the writer’s schema?

Người đọc lấy schema của người ghi ở đâu? But What Is the Writer’s Schema?

Tóm tắt

  • Không thể kèm nguyên schema vào từng bản ghi: schema thường to hơn dữ liệu nhiều lần.
  • File lớn nhiều bản ghi (Hadoop): ghi schema một lần ở đầu file, đó là object container file.
  • Database ghi từng bản ghi: đặt số phiên bản ở đầu mỗi bản ghi, lưu danh sách các phiên bản schema (như Espresso của LinkedIn).
  • Kết nối mạng: hai bên thương lượng phiên bản schema lúc bắt tay, dùng suốt kết nối (Avro RPC).

Câu hỏi bị lướt qua ở mục trước: với một bản ghi cụ thể, người đọc biết nó được ghi bằng schema nào bằng cách nào? Câu trả lời tuỳ ngữ cảnh. Ba ngữ cảnh điển hình trong sách được mô phỏng bên dưới, kèm phương án ngây thơ “nhét schema vào mỗi bản ghi” để so sánh.

Dù ở ngữ cảnh nào, một kho các phiên bản schema cũng rất đáng có: nó là tài liệu sống, và cho bạn cơ hội kiểm tra tương thích trước khi triển khai. Số phiên bản có thể là số nguyên tăng dần hoặc hash của schema.

Thực tế

Confluent Schema Registry cho Kafka làm đúng như phương án “database”: mỗi message bắt đầu bằng 1 byte magic và 4 byte schema ID; consumer tra ID trong registry rồi mới giải mã phần còn lại.

5.10 · Dynamically generated schemas · Code generation and dynamically typed languages

Schema sinh tự động và chuyện sinh code Dynamically Generated Schemas and Code Generation

Tóm tắt

  • Không có số tag giúp Avro hợp với schema sinh tự động: ví dụ dump một database quan hệ, mỗi bảng thành một record, mỗi cột thành một trường, tên cột thành tên trường.
  • Khi bảng đổi cột, chỉ cần sinh lại schema Avro. Trường được khớp theo tên nên người đọc cũ vẫn đối chiếu được.
  • Với Thrift/Protobuf, tag phải được gán tay và không bao giờ được gán lại; bộ sinh tự động phải nhớ mọi tag đã dùng.
  • Sinh code hữu ích cho ngôn ngữ tĩnh (Java, C++, C#); với ngôn ngữ động (JS, Ruby, Python) và schema sinh tự động thì nó là vật cản. Avro cho sinh code tuỳ chọn, và file container tự mô tả.

Vì sao việc không có vài con số trong schema lại quan trọng? Tưởng tượng bạn dump nội dung một database quan hệ ra file nhị phân (để tránh các vấn đề của JSON/CSV/SQL). Với Avro, sinh schema từ schema quan hệ rất dễ. Khi bảng được thêm một cột và bớt một cột, tiến trình export không cần quan tâm: lần chạy sau nó sinh schema mới từ schema database mới. Người đọc file mới thấy các trường đã đổi, nhưng vì trường khớp theo tên, schema người ghi mới vẫn ghép được với schema người đọc cũ.

Với Thrift hay Protobuf, mỗi lần schema database đổi, ai đó phải cập nhật tay ánh xạ “tên cột → tag”. Tự động hoá được, nhưng bộ sinh phải rất cẩn thận không gán lại tag đã từng dùng. Đây đơn giản không phải mục tiêu thiết kế của chúng, trong khi là mục tiêu của Avro.

Sinh code và ngôn ngữ động

Thrift và Protobuf dựa vào sinh code: có schema thì sinh class. Điều đó tốt cho ngôn ngữ kiểu tĩnh: cấu trúc trong bộ nhớ hiệu quả, có kiểm tra kiểu và gợi ý trong IDE. Với ngôn ngữ động thì không có trình kiểm tra kiểu nào cần thoả mãn, và một bước biên dịch thêm vào thường bị ghét. Avro cho phép sinh code nhưng không bắt buộc: một object container file chứa sẵn schema người ghi, nên bạn mở nó bằng thư viện Avro và xem dữ liệu như xem file JSON. File tự mô tả. Điều này đặc biệt hợp với ngôn ngữ xử lý dữ liệu động như Apache Pig: mở file Avro, phân tích, ghi kết quả ra Avro mà không cần nghĩ tới schema.

Cạm bẫy

Bộ sinh schema Protobuf “ngây thơ” gán tag theo thứ tự cột là một quả bom hẹn giờ: chỉ cần xoá một cột ở giữa, mọi tag phía sau dịch đi một, và dữ liệu cũ được đọc lặng lẽ sai nghĩa mà không có lỗi nào.

5.11 · The Merits of Schemas

Giá trị của schema The Merits of Schemas

Tóm tắt

  • Schema của Protobuf, Thrift, Avro đơn giản hơn XML Schema hay JSON Schema nhiều, nên được hỗ trợ trên rất nhiều ngôn ngữ.
  • Ý tưởng không mới: ASN.1 (chuẩn hoá 1984) đã có tag để tiến hoá schema, và mã hoá DER của nó vẫn dùng cho chứng chỉ X.509. Nhưng ASN.1 phức tạp, tài liệu kém.
  • Bốn lợi ích: gọn hơn “JSON nhị phân” (bỏ tên trường); schema là tài liệu luôn đúng; kho schema cho phép kiểm tra tương thích trước khi deploy; sinh code cho kiểm tra kiểu lúc biên dịch.

Nhiều hệ dữ liệu cũng có định dạng nhị phân riêng: phần lớn database quan hệ có giao thức mạng riêng, và nhà cung cấp phát hành driver (qua API ODBC, JDBC) để giải mã phản hồi thành cấu trúc trong bộ nhớ. Tức là mã hoá nhị phân dựa trên schema là lựa chọn rất thực tế, với các ưu điểm:

  • Gọn hơn nhiều so với các biến thể “JSON nhị phân”, vì bỏ được tên trường.
  • Schema là một dạng tài liệu quý, và vì bắt buộc phải có để giải mã, bạn chắc chắn nó cập nhật (tài liệu viết tay thì dễ lệch thực tế).
  • Giữ một kho schema cho phép kiểm tra tương thích xuôi/ngược của thay đổi trước khi triển khai bất cứ thứ gì.
  • Với ngôn ngữ kiểu tĩnh, sinh code từ schema cho phép kiểm tra kiểu lúc biên dịch.

Tóm lại, tiến hoá schema cho bạn sự linh hoạt giống database JSON schemaless/schema-on-read, đồng thời đảm bảo tốt hơn về dữ liệu và có công cụ tốt hơn. Bộ kiểm tra dưới đây làm đúng việc của một schema registry: nhận một đề xuất thay đổi và cho biết nó có được phép theo chế độ tương thích bạn yêu cầu hay không, theo đúng các luật Avro ở mục 5.8.

Ghi nhớ

Schema không đối lập với linh hoạt. Có schema và luật tiến hoá rõ ràng, bạn đổi dữ liệu thường xuyên hơn với ít sợ hãi hơn, vì máy kiểm tra hộ bạn.

5.12 · Modes of Dataflow · Dataflow Through Databases

Luồng dữ liệu qua database Dataflow Through Databases

Tóm tắt

  • Tương thích là quan hệ giữa tiến trình mã hoá và tiến trình giải mã. Có ba ngả dữ liệu chảy giữa các tiến trình: qua database, qua lời gọi dịch vụ, qua truyền thông điệp bất đồng bộ.
  • Ghi vào database giống như gửi thư cho chính mình trong tương lai: bắt buộc tương thích ngược. Nhiều tiến trình phiên bản khác nhau cùng truy cập, nên thường cần cả tương thích xuôi.
  • Cạm bẫy: code cũ đọc bản ghi có trường mới, sửa, ghi lại, và làm mất trường mới. Cần giữ nguyên các trường lạ.
  • Dữ liệu sống lâu hơn code: deploy xong trong vài phút, nhưng dữ liệu 5 năm tuổi vẫn nằm đó với định dạng cũ.

Từ đầu chương ta nói về việc gửi dữ liệu cho một tiến trình không chung bộ nhớ: ghi file, gửi qua mạng. Ai mã hoá, ai giải mã? Phần còn lại của chương xét ba ngả phổ biến:

NgảAi mã hoáAi giải mãKhoảng cách thời gian
Database (mục này)Tiến trình ghiTiến trình đọc, có thể rất lâu sauMili giây đến nhiều năm
REST/RPC (5.13–5.15)Client mã hoá request; server mã hoá responseServer, rồi clientCàng nhanh càng tốt
Message broker, actor (5.16)Người gửiNgười nhậnThường thấp, qua bộ đệm trung gian

Với database, nếu chỉ một tiến trình truy cập, người đọc là phiên bản sau của chính nó: lưu dữ liệu giống như gửi thư cho chính mình trong tương lai. Tương thích ngược rõ ràng là bắt buộc. Nhưng thường có nhiều tiến trình cùng truy cập (nhiều service, nhiều instance của một service), và trong lúc rolling upgrade, một giá trị có thể do code mới ghi rồi bị code cũ đọc. Nên tương thích xuôi cũng thường cần.

Cái bẫy “ghi đè làm mất trường”

Giả sử bạn thêm trường vào schema và code mới ghi giá trị cho trường đó. Sau đó code cũ (chưa biết trường mới) đọc bản ghi, sửa một chỗ, rồi ghi lại. Hành vi mong muốn thường là code cũ giữ nguyên trường mới dù không hiểu nó. Các định dạng ở trên hỗ trợ việc giữ trường lạ, nhưng đôi khi bạn phải cẩn thận ở tầng ứng dụng: nếu giải mã giá trị thành model object rồi mã hoá lại model object đó, trường lạ có thể rơi mất trong quá trình chuyển đổi. Không khó giải quyết, chỉ cần biết để tránh.

Dữ liệu ghi ở những thời điểm khác nhau

Database cho phép cập nhật bất kỳ giá trị nào vào bất kỳ lúc nào, nên trong cùng một database có giá trị ghi cách đây 5 mili giây và giá trị ghi cách đây 5 năm. Thay toàn bộ code mất vài phút; dữ liệu 5 năm tuổi thì vẫn ở định dạng gốc trừ khi bạn chủ động viết lại. Viết lại (migrate) toàn bộ dữ liệu sang schema mới thì được, nhưng đắt với tập dữ liệu lớn, nên phần lớn database tránh làm vậy. Hầu hết database quan hệ cho phép thêm cột với mặc định null mà không viết lại dữ liệu cũ (trừ MySQL, thường viết lại cả bảng); khi đọc hàng cũ, database điền null cho cột thiếu. Espresso của LinkedIn dùng Avro làm định dạng lưu trữ để tận dụng luật tiến hoá của Avro. Nhờ tiến hoá schema, cả database trông như được mã hoá bằng một schema duy nhất, dù bên dưới là bản ghi của nhiều thời kỳ.

Lưu trữ dài hạn

Khi chụp snapshot database (để backup hay nạp vào data warehouse, xem Chương 4), bản dump thường được mã hoá bằng schema mới nhất, dù dữ liệu gốc lẫn nhiều phiên bản: đằng nào cũng phải chép, chép cho đồng nhất luôn. Bản dump ghi một lần rồi bất biến, nên rất hợp với Avro object container file, hoặc định dạng cột như Parquet cho phân tích. Chương 11 sẽ bàn thêm.

Cạm bẫy

ORM là thủ phạm hay gặp của lỗi mất trường: nó ánh xạ hàng thành object chỉ có các thuộc tính đã khai báo, rồi UPDATE lại mọi cột hoặc ghi đè cả tài liệu JSON. Với document database, ưu tiên cập nhật từng phần ($set) thay vì ghi đè cả tài liệu.

5.13 · Dataflow Through Services: REST and RPC · Web services

Luồng dữ liệu qua dịch vụ: REST và SOAP Dataflow Through Services: Web Services

Tóm tắt

  • Kiểu sắp xếp phổ biến nhất: server phơi một API qua mạng (gọi là service), client kết nối tới để gửi request. Một server có thể là client của service khác: đó là kiến trúc hướng dịch vụ / microservices.
  • Khác database, service chỉ cho phép input/output mà logic nghiệp vụ định trước: một dạng đóng gói. Mục tiêu then chốt: mỗi service deploy và tiến hoá độc lập, nên client và server phiên bản cũ/mới chạy song song.
  • Dùng HTTP làm giao thức thì gọi là web service. Hai trường phái: REST (triết lý thiết kế dựa trên HTTP) và SOAP (giao thức dựa trên XML, mô tả bằng WSDL, dựa nặng vào sinh code).

Web chính là ví dụ quen thuộc: trình duyệt gửi GET để tải HTML, CSS, ảnh và POST để gửi dữ liệu; API ở đây là các chuẩn HTTP, URL, TLS, HTML mà mọi bên đồng ý. Nhưng client không chỉ là trình duyệt: app di động, app desktop, hay JavaScript trong trình duyệt (Ajax) đều gửi request và nhận về dữ liệu (thường là JSON) thay vì HTML. Lúc đó API là riêng của ứng dụng, và client với server phải thống nhất chi tiết.

Service giống database ở chỗ cho client gửi và truy vấn dữ liệu, nhưng thay vì cho phép truy vấn tuỳ ý, nó chỉ phơi ra API mà logic nghiệp vụ cho phép. Web service xuất hiện trong ba bối cảnh: app trên thiết bị người dùng gọi qua internet; service gọi service trong cùng tổ chức, thường cùng datacenter (phần mềm hỗ trợ việc này đôi khi gọi là middleware); và service gọi service của tổ chức khác (thanh toán thẻ, OAuth).

REST và SOAP

REST không phải giao thức mà là triết lý thiết kế dựa trên nguyên tắc của HTTP: định dạng dữ liệu đơn giản, URL để định danh tài nguyên, dùng tính năng của HTTP cho cache, xác thực, thương lượng kiểu nội dung. API theo REST gọi là RESTful; có thể mô tả bằng OpenAPI (Swagger). SOAP là giao thức dựa trên XML, cố độc lập với HTTP, kèm một rừng chuẩn WS-*. API SOAP được mô tả bằng WSDL, cho phép sinh code để gọi service từ xa như gọi method cục bộ. WSDL không dành cho người đọc, message SOAP khó viết tay, nên người dùng phụ thuộc nặng vào công cụ; tương tác giữa các nhà cung cấp hay trục trặc. SOAP vẫn còn ở doanh nghiệp lớn nhưng đã hết thời ở phần lớn công ty nhỏ.

Trong sách

SOAP không phải điều kiện của SOA dù tên na ná: SOAP là một công nghệ cụ thể, SOA là một cách tiếp cận chung để xây hệ thống.

5.14 · The problems with remote procedure calls (RPCs) · Current directions for RPC

Vì sao gọi qua mạng không giống gọi hàm The Problems with RPC

Tóm tắt

  • RPC (từ thập niên 1970) cố làm request qua mạng trông như gọi hàm trong cùng tiến trình. Ảo tưởng đó gọi là trong suốt vị trí. EJB, RMI, DCOM, CORBA đều dựa trên nó và đều có vấn đề lớn.
  • Request mạng khác hẳn gọi hàm: có thể mất request hoặc response; có thể timeout mà không biết bên kia đã làm chưa; retry có thể thực hiện hành động nhiều lần nếu không có tính luỹ đẳng; độ trễ cao và biến động; tham số phải mã hoá thành byte; hai bên có thể khác ngôn ngữ.
  • Thế hệ mới (gRPC, Finagle, Rest.li, Thrift, Avro RPC) thừa nhận khác biệt: dùng future/promise, stream, service discovery. REST vẫn thống trị API công khai; RPC chủ yếu dùng giữa các service cùng tổ chức.

Ý tưởng RPC rất hấp dẫn: charge(card, 100) dù chạy ở máy khác vẫn viết như gọi hàm. Nhưng theo sách, cách tiếp cận này sai từ gốc, vì một request mạng khác một lời gọi hàm cục bộ ở mọi khía cạnh quan trọng:

  • Gọi hàm thì dự đoán được: thành công hay thất bại chỉ phụ thuộc tham số bạn kiểm soát. Request mạng thì không: request hay response có thể mất, máy bên kia có thể chậm hoặc chết. Lỗi mạng là chuyện thường, nên bạn phải tính trước, ví dụ bằng retry.
  • Gọi hàm trả kết quả, ném exception, hoặc không bao giờ trả về (vòng lặp vô tận, tiến trình chết). Request mạng có thêm khả năng thứ tư: trả về mà không có kết quả vì timeout. Khi đó bạn không biết request đã tới nơi hay chưa (Chương 9 bàn kỹ).
  • Nếu retry, có thể request vẫn tới nơi, chỉ response bị mất. Retry sẽ thực hiện hành động nhiều lần, trừ khi giao thức có cơ chế khử trùng lặp (idempotence, Chương 12).
  • Gọi hàm tốn thời gian khá ổn định. Request mạng chậm hơn rất nhiều và biến động dữ dội: lúc nhanh dưới 1 ms, lúc mạng nghẽn hoặc service quá tải có thể mất nhiều giây.
  • Gọi hàm truyền được con trỏ tới object trong bộ nhớ. Request mạng phải mã hoá mọi tham số thành byte; ổn với số và chuỗi, rắc rối với object lớn.
  • Client và service có thể viết bằng ngôn ngữ khác nhau, nên framework phải dịch kiểu dữ liệu, và kết quả có thể xấu (nhớ chuyện số lớn hơn 253 trong JavaScript ở mục 5.3).

Vì vậy không nên cố làm service từ xa trông giống object cục bộ. Một phần sức hút của REST là nó không giấu việc mình là giao thức mạng.

Hướng đi hiện nay của RPC

Dù vậy RPC không biến mất. Có framework RPC trên mọi định dạng của chương: Thrift và Avro có sẵn RPC, gRPC dùng Protocol Buffers, Finagle dùng Thrift, Rest.li dùng JSON qua HTTP. Thế hệ mới nói thẳng rằng gọi từ xa khác gọi cục bộ: Finagle và Rest.li dùng future (promise) để bọc hành động bất đồng bộ có thể thất bại, tiện cả khi cần gọi song song nhiều service rồi gộp kết quả; gRPC hỗ trợ stream (một lời gọi gồm chuỗi request và response theo thời gian). Một số framework có service discovery: cho client biết service đang ở IP và port nào (Chương 7).

RPC nhị phân tự thiết kế có thể nhanh hơn JSON qua REST. Nhưng REST có lợi thế lớn khác: dễ thử nghiệm và debug (gõ curl hoặc mở trình duyệt là xong), mọi ngôn ngữ đều hỗ trợ, và có cả hệ sinh thái công cụ: server, cache, load balancer, proxy, firewall, giám sát, kiểm thử. Vì thế REST thống trị API công khai, còn RPC tập trung vào request giữa các service cùng tổ chức, thường cùng datacenter.

Ghi nhớ

Bốn kết cục của request mạng: thành công, lỗi, không bao giờ trả về, và không biết. Kết cục thứ tư buộc bạn phải thiết kế thao tác sao cho thực hiện lại cũng an toàn.

5.15 · Data encoding and evolution for RPC

Tiến hoá dữ liệu trong RPC và phiên bản API Data Encoding and Evolution for RPC

Tóm tắt

  • Giả định hợp lý: server được nâng cấp trước, client sau. Vậy chỉ cần tương thích ngược cho request và tương thích xuôi cho response.
  • Tính tương thích của RPC thừa hưởng từ định dạng mã hoá: Thrift, gRPC, Avro RPC theo luật của định dạng; SOAP theo XML Schema (có bẫy); REST thường dùng JSON không schema: thêm tham số tuỳ chọn và thêm trường vào response được coi là an toàn.
  • Khi service phục vụ client của tổ chức khác, bạn không ép được họ nâng cấp, nên phải giữ tương thích rất lâu, có khi mãi mãi, và đôi khi chạy song song nhiều phiên bản API.
  • Chưa có chuẩn chung cho phiên bản API: số phiên bản trong URL, trong header Accept, hoặc lưu phiên bản theo API key ở phía server.

Với dataflow qua database, mọi tổ hợp code/dữ liệu cũ/mới đều có thể xảy ra. Với dịch vụ, ta có một giả định đơn giản hoá: nâng cấp hết server trước, rồi đến client. Khi đó, request từ client cũ tới server mới (cần tương thích ngược trên request), và response từ server mới tới client cũ (cần tương thích xuôi trên response).

Khó khăn lớn hơn khi API vượt ra ngoài tổ chức: nhà cung cấp không kiểm soát client. Nếu bắt buộc phải có thay đổi phá vỡ tương thích, họ thường phải duy trì nhiều phiên bản API cạnh nhau. Client chọn phiên bản bằng cách nào thì chưa có đồng thuận. Với REST, phổ biến là số phiên bản trong URL hoặc trong header Accept. Với service định danh client bằng API key, còn một cách: lưu phiên bản mà client yêu cầu ở phía server, và cho phép đổi phiên bản qua một giao diện quản trị riêng (cách của Stripe).

Thực tế

Stripe ghim mỗi tài khoản vào phiên bản API tại thời điểm tích hợp lần đầu; client có thể ghi đè từng request bằng header Stripe-Version và nâng cấp chủ động trong dashboard. Server phía sau chuyển đổi response qua một chuỗi “bộ dịch phiên bản”.

5.16 · Message-Passing Dataflow · Message brokers · Distributed actor frameworks

Truyền thông điệp bất đồng bộ: broker và actor Message-Passing Dataflow

Tóm tắt

  • Truyền thông điệp nằm giữa RPC và database: thông điệp đến người nhận với độ trễ thấp như RPC, nhưng đi qua một trung gian lưu tạm, là message broker, giống database.
  • Lợi ích so với RPC trực tiếp: làm bộ đệm khi người nhận chết hoặc quá tải; tự gửi lại khi tiến trình nhận bị crash; người gửi không cần biết IP/port; một thông điệp tới nhiều người nhận; tách rời người gửi và người nhận.
  • Thường là một chiều và bất đồng bộ: gửi xong là quên. Broker không áp mô hình dữ liệu; thông điệp chỉ là byte, nên dùng định dạng tương thích hai chiều thì deploy producer/consumer theo thứ tự nào cũng được.
  • Mô hình actor phân tán dùng cùng cơ chế thông điệp giữa các node; rolling upgrade vẫn cần tương thích xuôi và ngược.

Message broker

Trước đây thị trường do phần mềm thương mại của TIBCO, IBM WebSphere, webMethods thống trị; gần đây là mã nguồn mở: RabbitMQ, ActiveMQ, HornetQ, NATS, Apache Kafka (so sánh chi tiết ở Chương 12). Cách dùng chung: một tiến trình gửi thông điệp tới một queue hoặc topic có tên, broker đảm bảo nó tới một hoặc nhiều consumer/subscriber. Một topic có thể có nhiều producer và nhiều consumer. Topic chỉ chảy một chiều, nhưng consumer có thể publish tiếp sang topic khác, hoặc vào một reply queue mà người gửi ban đầu đọc (tạo ra luồng request/response giống RPC). Nếu consumer publish lại thông điệp, hãy cẩn thận giữ các trường lạ, kẻo gặp lại lỗi mất trường của mục 5.12.

Framework actor phân tán

Mô hình actor là mô hình lập trình đồng thời trong một tiến trình: thay vì làm việc trực tiếp với thread (và race condition, lock, deadlock), logic được gói trong các actor. Mỗi actor thường đại diện cho một client hay thực thể, có trạng thái cục bộ không chia sẻ, và giao tiếp bằng thông điệp bất đồng bộ. Việc gửi không được đảm bảo: trong một số tình huống lỗi, thông điệp bị mất. Mỗi actor xử lý một thông điệp một lúc, nên không phải lo về thread.

Framework actor phân tán dùng cùng cơ chế để mở rộng ra nhiều node: nếu người gửi và người nhận ở hai node khác nhau, thông điệp được mã hoá thành byte, gửi qua mạng, giải mã ở bên kia. Trong suốt vị trí ở đây ổn hơn RPC, vì mô hình actor vốn đã giả định thông điệp có thể mất ngay cả trong một tiến trình. Nhưng khi rolling upgrade ứng dụng actor, thông điệp vẫn đi từ node mới tới node cũ và ngược lại:

  • Akka mặc định dùng serialization có sẵn của Java, không tương thích xuôi hay ngược; thay bằng Protocol Buffers thì rolling upgrade được.
  • Orleans mặc định dùng định dạng riêng không hỗ trợ rolling upgrade: phải dựng cluster mới, chuyển traffic sang, rồi tắt cluster cũ. Cũng có thể cắm serializer khác.
  • Erlang OTP: đổi schema bản ghi khó đến bất ngờ dù hệ thống có nhiều tính năng cho tính sẵn sàng cao; rolling upgrade được nhưng phải lên kế hoạch cẩn thận. Kiểu maps (giống JSON, từ Erlang R17 năm 2014) có thể giúp dễ hơn.
Ghi nhớ

Ba ngả dataflow, cùng một yêu cầu: mọi byte chảy trong hệ thống phải được mã hoá sao cho code mới đọc được dữ liệu cũ và code cũ đọc được dữ liệu mới. Làm được điều đó thì rolling upgrade, deploy thường xuyên và tiến hoá độc lập trở thành chuyện bình thường.

5.★ · Summary

Tổng kết và tự kiểm tra Summary

Chương này xem xét nhiều cách biến cấu trúc dữ liệu thành byte trên mạng hoặc trên đĩa, và thấy rằng chi tiết mã hoá không chỉ ảnh hưởng hiệu năng, mà quan trọng hơn là ảnh hưởng kiến trúc ứng dụng và cách bạn triển khai nó. Rolling upgrade cho phép release không downtime (khuyến khích release nhỏ và thường xuyên) và giảm rủi ro (phát hiện, rollback bản lỗi trước khi ảnh hưởng nhiều người). Muốn vậy, mọi dữ liệu chảy trong hệ thống phải tương thích ngược và xuôi.

  • Định dạng riêng của ngôn ngữ: trói vào một ngôn ngữ, thường không tương thích phiên bản, nguy hiểm khi giải mã dữ liệu lạ.
  • JSON, XML, CSV: phổ biến, tương thích tuỳ cách dùng, schema tuỳ chọn; mơ hồ về kiểu, cẩn thận với số và chuỗi nhị phân.
  • Thrift, Protocol Buffers, Avro: gọn, hiệu quả, ngữ nghĩa tương thích rõ ràng; schema là tài liệu và nguồn sinh code. Nhược điểm: phải giải mã mới đọc được bằng mắt.

Ba ngả dataflow: database (người ghi mã hoá, người đọc giải mã, có thể cách nhau nhiều năm); RPC và REST (client mã hoá request, server giải mã rồi mã hoá response, client giải mã); truyền thông điệp bất đồng bộ qua broker hoặc actor. Với một chút cẩn thận, tương thích hai chiều và rolling upgrade hoàn toàn trong tầm tay.

Đang rolling upgrade: node chạy code v1 đọc một bản ghi do node v2 ghi. Đây là yêu cầu tương thích gì?

  1. Tương thích ngược
  2. Tương thích xuôi
  3. Không cần tương thích vì cùng một database

Code cũ đọc dữ liệu mới là tương thích xuôi (forward). Tương thích ngược là code mới đọc dữ liệu cũ. Trong rolling upgrade cả hai đều xảy ra.

Vì sao số 9007199254740993 trong JSON có thể bị đọc thành 9007199254740992?

  1. JSON chỉ cho phép số 32-bit
  2. JSON bắt buộc mọi số là số thực
  3. JSON không quy định độ chính xác; JavaScript đọc số bằng double IEEE 754, chỉ chính xác tới 253

JSON không phân biệt số nguyên/số thực và không nói gì về độ chính xác. Parser của JavaScript chuyển mọi số thành double, mà double có 53 bit phần định trị.

Bản ghi ví dụ chiếm 66 byte với MessagePack nhưng chỉ 33 byte với Protocol Buffers. Nguồn tiết kiệm lớn nhất là gì?

  1. Protobuf không ghi tên trường, chỉ ghi field tag
  2. Protobuf nén chuỗi bằng gzip
  3. Protobuf bỏ qua trường interests

Tên “userName”, “favoriteNumber”, “interests” chiếm phần lớn khác biệt. Có schema, dữ liệu chỉ cần mang tag (1 byte mỗi trường). Varint giúp thêm một chút với số 1337.

Trong Protocol Buffers, thao tác nào không bao giờ an toàn?

  1. Đổi tên một trường nhưng giữ tag
  2. Thêm trường optional với tag mới
  3. Xoá một trường rồi dùng lại tag của nó cho trường mới

Dữ liệu cũ vẫn mang tag cũ; dùng lại tag khiến dữ liệu cũ bị hiểu theo nghĩa mới mà không có lỗi nào. Đổi tên an toàn vì dữ liệu không chứa tên; thêm trường optional an toàn cả hai chiều.

Với Avro, schema người đọc có trường email không có giá trị mặc định, nhưng schema người ghi không có trường này. Điều gì xảy ra?

  1. Trường được điền null
  2. Giải mã thất bại: đây là thay đổi phá vỡ tương thích ngược
  3. Avro dùng tag để tìm giá trị gần nhất

Trường người đọc cần mà người ghi không có thì lấy default của schema người đọc; không có default thì lỗi. Null chỉ là default khi trường là union có nhánh null đầu tiên và khai báo default null.

Vì sao Avro hợp với việc dump database có cột thay đổi thường xuyên hơn Protobuf?

  1. Schema Avro không có tag; trường khớp theo tên nên có thể sinh lại schema tự động mỗi lần
  2. Avro không cần schema
  3. Avro luôn kèm schema vào từng bản ghi

Protobuf cần ánh xạ tên cột → tag được duy trì cẩn thận, không bao giờ gán lại. Avro dùng tên, và object container file chỉ kèm schema một lần ở đầu file.

Client gọi chargeCard, bị timeout, rồi retry, và khách bị trừ tiền hai lần. Nguyên nhân và cách sửa?

  1. Request đầu bị mất; cần tăng timeout
  2. Server chạy chậm; cần thêm server
  3. Request đầu tới nơi nhưng response bị mất; cần khoá luỹ đẳng để server khử trùng lặp

Timeout nghĩa là không biết. Nếu chỉ response mất thì retry thực hiện lại hành động. Khoá luỹ đẳng (idempotency key) cho phép server nhận ra request lặp và trả lại kết quả cũ.

Giả định “server nâng cấp trước, client sau” cho RPC dẫn đến yêu cầu nào?

  1. Tương thích xuôi cho request, ngược cho response
  2. Tương thích ngược cho request, xuôi cho response
  3. Chỉ cần tương thích ngược cho cả hai

Server mới phải đọc request từ client cũ (ngược trên request); client cũ phải đọc response từ server mới (xuôi trên response).
